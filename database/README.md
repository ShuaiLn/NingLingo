# NingLingo Cloud database

`migrations/001_…017_*.sql` is the ordered, reproducible PostgreSQL schema. These files are tested against embedded PostgreSQL with Supabase Auth identity stubs; neither Docker nor local Supabase is used. Tests do not imply that migrations have been applied to Cloud.

The owner applied 001–017 directly to Cloud, including `013_alphabet_quiz.sql` and the subsequent 014–017 expansion on October 12, 2026. The expansion's live schema and behavior were verified without DDL or migration replay. Read-only Data API inspection cannot access the private checksum ledger; never infer that SQL is unapplied from missing ledger access. The owner also supplied the read-only SQL Editor catalog output for full definition review. Migration `012_reading_conflict_errors.sql` preserves both Reading functions and their grants while replacing retryable application-conflict errors (`40001`) with non-retryable `22023`. Original migrations remain immutable. Do not rerun migrations 001–017 or assume manually applied SQL populated the runner's checksum-history table.

Run `node scripts/migrate-cloud.mjs --check` to validate the file sequence without connecting. `node scripts/migrate-cloud.mjs` applies each unapplied migration transactionally through the [Supabase Management API](https://supabase.com/docs/reference/api/v1-run-a-query), records SHA-256 checksums in the private `ninglingo_internal.applied_migrations` table, refuses rewritten/out-of-order history, and verifies the resulting history. It requires an authorized server-side `SUPABASE_ACCESS_TOKEN` with database write access. The project reference is derived from the existing `NEXT_PUBLIC_SUPABASE_URL`; `SUPABASE_PROJECT_REF` is only necessary for a custom Supabase API domain. Publishable and secret/service-role Data API keys cannot execute DDL. The runner never prints credential values.

The Auth schema, `auth.users`, `auth.uid()`, `auth.jwt()`, and `anon` / `authenticated` / `service_role` roles are provided by Supabase Cloud. Do not recreate their embedded-test substitutes in Cloud. Migrations bootstrap profiles for existing admin-provisioned users and attach an Auth insert trigger for later accounts. User-data defaults never seed mock vocabulary or mock users.

All 26 exposed domain tables enable RLS after migration 013; migrations 014–017 produce 29 domain tables, all with RLS. Personal reads use `auth.uid()` ownership. Composite foreign keys enforce owner/language consistency. Human-reviewed `published` Grammar requires a human review record. Migration 014 separately permits accurately disclosed `published-ai` lessons without manufacturing reviewer records; drafts/review-only content and its examples/exercises/sources remain hidden from signed-in product clients. No anonymous table/function access is granted. Users cannot write quiz grades, SRS stages, machine cache, grammar content, or completion scores directly. Functions pin the search path and explicitly check ownership; service-only quiz CAS/content imports are not executable by authenticated or anonymous callers.

Vocabulary import runs in one transaction, preserves canonical Unicode duplicate identity, and serializes imports per owner. Reading edits lock/check the expected body version; positional annotations use UTF-16 code units, reject split surrogate pairs, and must be explicitly cleared on a body change. The legacy `example` CSV column remains supported alongside relational translated examples and the six explicit relation types added in migration 006.

Quiz scheduler/grading remain in the tested server-side domain engine. Service-only `nl_create_quiz` and `nl_commit_quiz` persist its immutable snapshot and relational state, check answer replay before optimistic versions, lock sessions and progress, validate frozen answers again, record learning-day activity, and settle each tested word once. Progress locks use stable UUID order. Live vocabulary deletion does not alter historical snapshots or resurrect deleted words. Early practice preserves due dates; same-day promotion guards survive later errors.

Grammar `nl_import_grammar` accepts the typed `GrammarPoint[]` manifest, stores normalized relational versions/children, validates minimum counts and unique exercise options, refuses changed content under an existing version, and never manufactures reviewer records for drafts. `nl_submit_grammar` grades against published content, retains completion after a later weaker score, and records progress independently for each content version.

Useful read RPCs: `nl_profile`, `nl_vocabulary_entries`, `nl_progress_words`, and `nl_grammar_points`. Mutation RPCs: `nl_save_vocabulary`, `nl_import_vocabulary`, `nl_save_reading`, `nl_annotate_reading`, `nl_submit_grammar`. Server-only RPCs: `nl_create_quiz`, `nl_commit_quiz`, `nl_import_grammar`. All JSON responses use the application's existing camelCase domain models.

Migration `013_alphabet_quiz.sql` adds independent Alphabet sessions/attempts, immutable content versions and item/template/configuration snapshots, optimistic versions and submission replay protection. `nl_create_alphabet_quiz` and `nl_commit_alphabet_quiz` are service-only. Alphabet answers record timezone-aware `alphabet-quiz` activity without updating vocabulary progress or review settlements. Only session creation reads static Alphabet content; grading, retries, hints and resume use saved content.

The same migration adds `translation_cache.lookup_kind` (`reading` by default for existing rows; `vocabulary` for context-free word lookups), an English-only target and namespace-aware uniqueness. Vocabulary rows require empty context. Reading retains its contextual cache keys and ignores vocabulary records. CSV previews never create vocabulary/SRS records; confirmed resolved rows continue through one `nl_import_vocabulary` transaction.

Migration 013 is already applied to the connected project. Its historical verification executed no DDL and did not import or publish grammar. See [that verification report](../docs/ALPHABET_CSV_VERIFICATION.md) for its results.

Migrations 014–017 add Korean/AI lesson publication, mixed quiz question metadata and participating-language history, owner-scoped word pairs with deletion tombstones, owner-scoped care/preferences and new-answer care reactivation, immutable session presentation, and frozen Alphabet MCQ grading. Applied migrations 001–013 remain unchanged. Read the [learning expansion report](../docs/LEARNING_EXPANSION_VERIFICATION.md) for current application and validation status.

`npm run db:inspect` performs read-only schema probes and inventories published grammar. `verify_expansion_schema.sql` is a single read-only catalog SELECT for SQL Editor; `scripts/compare-cloud-schema.mjs` can compare supplied JSON files locally. `npm run test:cloud:extensions` exercises real repositories, cloud RPCs, three production-browser contexts, grading/history/SRS/publication and owner isolation using disposable accounts and temporary grammar fixtures, then verifies cleanup. Its expansion verification passed 537 checks.

The configured cloud now contains **60/60 Korean production lessons**, all `published-ai`, with 180 translated examples, 300 exercises and no human-review records. The user-authorized `npm run grammar:publish:ko` imported only the existing Korean manifests; an identical replay produced 0 inserts and 60 unchanged lessons. `npm run grammar:verify:ko` checks all sixty under ordinary authenticated RLS and verifies SHA-256 integrity of every original Japanese/Spanish/Greek point, version, example, exercise, source and review record. Add `-- --browser` to inspect the production build against real cloud content. These checks passed, and both disposable publication-verification accounts were removed. No migration was replayed and no unrelated production user data was modified.

The SQL runner inspects schema and checksum history before DDL and refuses an incomplete legacy baseline instead of replaying old migrations. A secret/service-role Data API key cannot replace SQL management credentials or verify the private checksum ledger.
