# NingLingo Cloud database

`migrations/001_…012_*.sql` is the ordered, reproducible PostgreSQL schema. These files are tested against embedded PostgreSQL with Supabase Auth identity stubs; neither Docker nor local Supabase is used. Tests do not imply that migrations have been applied to Cloud.

The owner applied 001–011 directly to Cloud. Live verification found that Reading version conflicts raised SQLSTATE `40001`, triggering PostgREST transaction retries. Apply **only `012_reading_conflict_errors.sql`** to that existing project: it preserves both Reading functions and their grants while replacing application-conflict errors with non-retryable `22023`. Original migrations remain immutable. Do not rerun initial migrations or assume manually applied SQL populated the runner's checksum-history table.

Run `node scripts/migrate-cloud.mjs --check` to validate the file sequence without connecting. `node scripts/migrate-cloud.mjs` applies each unapplied migration transactionally through the [Supabase Management API](https://supabase.com/docs/reference/api/v1-run-a-query), records SHA-256 checksums in the private `ninglingo_internal.applied_migrations` table, refuses rewritten/out-of-order history, and verifies the resulting history. It requires an authorized server-side `SUPABASE_ACCESS_TOKEN` with database write access. The project reference is derived from the existing `NEXT_PUBLIC_SUPABASE_URL`; `SUPABASE_PROJECT_REF` is only necessary for a custom Supabase API domain. Publishable and secret/service-role Data API keys cannot execute DDL. The runner never prints credential values.

The Auth schema, `auth.users`, `auth.uid()`, `auth.jwt()`, and `anon` / `authenticated` / `service_role` roles are provided by Supabase Cloud. Do not recreate their embedded-test substitutes in Cloud. Migrations bootstrap profiles for existing admin-provisioned users and attach an Auth insert trigger for later accounts. User-data defaults never seed mock vocabulary or mock users.

All 24 exposed domain tables enable RLS. Personal reads use `auth.uid()` ownership. Composite foreign keys enforce owner/language consistency. Published Grammar requires a human review record; drafts/review-only content and its examples/exercises/sources are hidden from signed-in product clients. No anonymous table/function access is granted. Users cannot write quiz grades, SRS stages, machine cache, grammar content, or completion scores directly. Functions pin the search path and explicitly check ownership; service-only quiz CAS/content imports are not executable by authenticated or anonymous callers.

Vocabulary import runs in one transaction, preserves canonical Unicode duplicate identity, and serializes imports per owner. Reading edits lock/check the expected body version; positional annotations use UTF-16 code units, reject split surrogate pairs, and must be explicitly cleared on a body change. The legacy `example` CSV column remains supported alongside relational translated examples and the six explicit relation types added in migration 006.

Quiz scheduler/grading remain in the tested server-side domain engine. Service-only `nl_create_quiz` and `nl_commit_quiz` persist its immutable snapshot and relational state, check answer replay before optimistic versions, lock sessions and progress, validate frozen answers again, record learning-day activity, and settle each tested word once. Progress locks use stable UUID order. Live vocabulary deletion does not alter historical snapshots or resurrect deleted words. Early practice preserves due dates; same-day promotion guards survive later errors.

Grammar `nl_import_grammar` accepts the typed `GrammarPoint[]` manifest, stores normalized relational versions/children, validates minimum counts and unique exercise options, refuses changed content under an existing version, and never manufactures reviewer records for drafts. `nl_submit_grammar` grades against published content, retains completion after a later weaker score, and records progress independently for each content version.

Useful read RPCs: `nl_profile`, `nl_vocabulary_entries`, `nl_progress_words`, and `nl_grammar_points`. Mutation RPCs: `nl_save_vocabulary`, `nl_import_vocabulary`, `nl_save_reading`, `nl_annotate_reading`, `nl_submit_grammar`. Server-only RPCs: `nl_create_quiz`, `nl_commit_quiz`, `nl_import_grammar`. All JSON responses use the application's existing camelCase domain models.
